# v1.5.0

Through 1.4.2, every connection was assumed to be IRIS. Caché, Ensemble and HealthShare
instances only speak Atelier v1, and the IRIS-shaped endpoints they do serve misbehave in
ways that read as iad bugs: `/action/search` always returns an empty result (verified against
a document containing the query term), and `/docnames/CLS` times out server-side on a
51k-class namespace. This release reads the product family off the server and answers those
calls from the SQL data dictionary, so one binary now works against a Caché 2016.2.3
instance and a current IRIS one.

Also new: `iris_sync` — save-sync, the VS Code ObjectScript plugin's save-on-write behavior
for agents that edit local files but have no editor compiling them on save.

## What's new

### Caché-family compatibility (Atelier v1)

The Atelier root reports a product string; iad parses it (`IrisProduct`, fail-open on
`Unknown`) and branches when it names the Caché family. The branches answer from the SQL
data dictionary where the v1 endpoints lie or hang:

- class and routine listings (`iris_info`, `iris_doc` list, `fetch_class_list`) read
  `%Dictionary.ClassDefinition` and `%Library.RoutineIndex`
- `iris_search` matches names, properties and methods against the dictionary instead of the
  endpoint that always returns nothing
- mirror tools return `UNSUPPORTED_ON_CACHE` — `%SYSTEM.Mirror` is IRIS-only

`check_config` reports the product family, so "why does this instance behave differently"
has an answer in the tool output. IRIS paths are untouched — the gate only fires on
`is_cache_family()`.

Two Caché-side fixes ride with the layer, listed below: `iris_test` no longer reports fake
passes, and `iris_table_info` reads storage globals for `%CacheSQLStorage` classes.

### `iris_sync` — save-sync

Upload a local file to the server and compile it when the type needs compiling: `.cls` /
`.mac` / `.int` / `.inc` / `.csp` upload + compile, static web files (`.js` / `.css` /
`.html` / `.svg` / `.json`) upload only. Write-gated like `iris_compile`, reached through
the same gate.

Path mapping is relative to the workspace root: `src/ABN/X.cls` → `ABN.X.cls` (the `Class`
declaration wins when it names a different class), `src/Nur/F.inc` → `Nur.DateFormat.inc`.
Web files go through an explicit mapping:

```toml
[sync]
flags = "cuk"

[[sync.web_roots]]
local  = "src/dthealth/web"
server = "/dthealth/web"
```

An unmapped web root is refused with `NOT_SYNCABLE`, never a guessed server path — the
server this was built against (Caché 2016.2.3) answers nothing useful on `/cspapps`, so
guessing would silently upload to the wrong place. Compile errors return `COMPILE_ERROR`
with the full compiler console, so the local file can be fixed and re-synced.

The `sync` subcommand is the CLI entry point, and `sync --hook` is the Claude Code
PostToolUse entry point: it reads one `{"tool_input":{"file_path":"..."}}` payload from
stdin and exits 2 on failure, which is the hook contract for feeding stderr back to the
model — a compile error lands in the conversation, the model fixes the file, the next save
re-syncs.

Two details from testing against live v1 servers, both in the code because they cost an
afternoon each: document names containing slashes must be PUT with the slashes literal
(`/doc//dthealth/web/csp/x.js`) — encoding them as `%2F` gets an Apache 404 that reads as
"document not found" — and a failed PUT on v1 can return HTTP 200 with the failure only in
`result.status`, so both `status.errors` and `result.status` are checked.

The catalog grows by one tool per tier: 85 / 81 / 82 tools for baseline / nostub / merged,
95 KB to 107 KB of JSON.

### CLI subcommands take the namespace from the resolved connection

`compile`, `exec`, `doc` and `query` passed clap's `USER` default explicitly as a tool
parameter, and the parameter takes precedence — so a workspace toml that configured
`namespace = "HIS"` was silently overridden and everything ran in USER. All four now read
the namespace off the resolved connection.

## Notable fixes

### `iris_test` ran zero classes on Caché and reported "All PASSED"

Caché's `%UnitTest.Manager` is not the IRIS one. `/verbose` does not exist (Error #5001
kills the run before any test executes), and a bare class name in `testspec` resolves as a
directory under `^UnitTestRoot` — zero classes run and the run still ends "All PASSED".

The Caché branch resolves the pattern to concrete classes via the SQL dictionary (single
class names go straight through, globs are capped at 50 → `TOO_MANY_TEST_CLASSES`), then
issues one colon-syntax `RunTest(":Pkg.Class")` per class with
`/noload/nodelete/norecursive/displaylog`. Directory-path patterns and
`test_type="testproduction"` return `UNSUPPORTED_ON_CACHE` rather than silently running
nothing.

### `iris_table_info` reported null storage globals for `%CacheSQLStorage` classes

`%Dictionary.CompiledStorage` has no `DataLocation`/`IndexLocation` for classes using the
legacy SQL mapping common in Caché-era schemas (`SQLUser.PA_PatMas` → `User.PAPatMas`), so
the tool reported null globals for tables that plainly have them. When the dictionary
answers empty, the class source is fetched and the Storage block parsed instead: data
global from the `<SQLMap Type="data">` map's `<Global>`, index globals from the
`<SQLMap Type="index">` maps — a plain string when they share one global, an array in
first-seen order when they differ. `{%%PARENT}` placeholder DataLocations are skipped; they
say nothing about this class's own global. Default-storage classes still answer from the
dictionary; the fallback only fires on an empty answer.

### Server-side hooks that hijacked the generator's output device

Server-side source-control hooks (iMedical on Caché 2016.2.3) redirect the current device
mid-body — even `Write "hello"` left it pointing at the hook's mirror file, and the old
guard turned that into `ERROR($DEVICE)` on every generator-backed call. The wrapper now
closes the hijacked device (so its buffer flushes), links the file, and reads the contents
back; mirror hooks that already copied the capture file's text are detected so the output
is not duplicated.

A drift to a non-file device (terminal, TCP) still fails loudly — `recovered` is set only
when the read produced text, and the body's trailing sentinel guarantees a readable
hijacked file has at least one line, so an empty read cannot masquerade as success.

### The WCM failure reason was discarded right where it was needed

The Windows credential path logged "WCM lookup failed … trying state.vscdb fallback" but
discarded the failure that triggered the fallback, so the diagnostic dead-ended exactly
where the answer was. The reason now rides along in the debug line.

### The CLI handed out WebSocket tokens nothing could use

`iris-agentic-dev tool iris_ws_open` opened a session, printed a token, and exited. The
token was a handle into a pool of live sockets held in that process's memory, so the next
command answered `SESSION_STALE: Session token references an unknown server or expired
session` — a timeout that had not happened, against a server that was fine.

`tool` refuses `iris_ws_open`, `iris_ws_exec` and `iris_ws_close` now, before it resolves a
connection, and the refusal carries the `batch` script that works:

```bash
echo '[{"tool":"iris_ws_open","args":{}},
       {"tool":"iris_ws_exec","args":{"session":"{{0.session}}","code":"Set x=1"}},
       {"tool":"iris_ws_exec","args":{"session":"{{0.session}}","code":"Write x"}},
       {"tool":"iris_ws_close","args":{"session":"{{0.session}}"}}]' | iris-agentic-dev batch
```

`batch` has been there since 1.3.0 and appeared in no documentation at all — `grep batch
README.md docs/*.md` found nothing. It is in the README command list, the troubleshooting
subcommand table, and a troubleshooting section of its own now, and `docs/tools.md` explains
the process boundary where the session tools are documented.

### `iris_servers` reports the URL it actually calls

Every entry now carries `base_url`, prefix included. `docs/tools.md` has said "every entry
carries `base_url`, the URL iad actually calls" since 1.4.2 and step 5 of the 116 plan
called for it, but the listing never emitted the key — two instances behind one gateway
still came back as the same host and port with nothing to tell them apart.

## Breaking changes

`iris-agentic-dev tool iris_ws_open` exits 1 instead of printing a session token. Any
script that read the token out of it was already broken — the very next call it made
returned `SESSION_STALE`. Under MCP the three tools are unchanged.
